Avancée : l’instruction associée à l’échec F4 est identifiée dans la DLL récupérée.
Blocage : la cause de son rejet par Prism et la faisabilité du build portable restent à démontrer.
Décision : proposer une reprise native CPU limitée, avant toute reconstruction et sous réserve de l’accord utilisateur.

## Diagnostic F4

Sur la réservation Snapdragon X Plus X1P42100, Windows 11 ARM64 build 26200, l’événement Application Error pour le worker PID 1568 indique `ggml-cpu.dll`, exception `0xc000001d`, offset module `0x470a`. Le SHA-256 de cette DLL est `f7546413e1e6e248df0bc8a0745a414de4c36532b201b3ba219d86864b5f1ab0`. La DLL PE a une section `.text` de RVA `0x1000` et offset brut `0x400` ; l’offset WER donne l’offset fichier `0x3b0a`, octets `c5 f8 10 44 24 20`, désassemblés `vmovups xmm0, xmmword ptr [rsp+20h]`. Cet encodage VEX.128 relève d’AVX, sans démontrer un défaut AVX2. Le code d’exception indique une instruction illégale ; les capacités CPUID/XGETBV et réglages Prism du processus fautif ne sont pas connus. La cause exacte du refus de l’AVX n’est pas établie.

Microsoft indique que Prism Windows 11 24H2 et ultérieur prend en charge AVX/AVX2, avec une option pouvant masquer les fonctions récentes : [documentation](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-program-compat-troubleshooter). Ce constat ne garantit pas la configuration de la réservation F4 ni le fonctionnement des autres instructions. Les preuves récupérées sont conservées sous `deliverables/parakeet-faisabilite/076a63c097ca49d881fd1534b093c685/` et l’archive du même dossier.

## Solution proposée

Produire d’abord un jeu CPU Windows x64 générique dont le socle compilateur est SSE2, puis qualifier sa compatibilité et ses performances. Conserver un chemin GPU distinct ; aucun rebuild GPU n’est inclus dans ce mandat. La suppression d’AVX de ce premier candidat réduit le risque identifié et demande une vérification du code effectivement produit et de ses dépendances.

Dans les sources épinglées, `GGML_NATIVE=OFF` seul peut laisser actives des options ISA. Le profil MSVC portable proposé fixe explicitement à OFF : `GGML_NATIVE`, `GGML_SSE42`, `GGML_AVX`, `GGML_AVX2`, `GGML_BMI2`, `GGML_AVX_VNNI`, `GGML_AVX512`, `GGML_AVX512_VBMI`, `GGML_AVX512_VNNI`, `GGML_AVX512_BF16`, `GGML_CPU_ALL_VARIANTS`, `GGML_BACKEND_DL` et `GGML_CUDA`. Les options AMX, FMA et F16C ne sont pas déclarées sous MSVC dans ce commit : contrôler l’absence de leurs macros et flags effectifs plutôt que demander leur présence dans le cache CMake. Préserver `/MD`, `/Brepro`, les sources, patches et versions épinglés. Vérifier les options et définitions réellement disponibles, ainsi que toute option additionnelle susceptible de générer des instructions avancées ; en cas de contradiction, arrêter avant compilation. Sous MSVC x64, SSE2 est la base sans `/arch` avancé : [documentation Microsoft](https://learn.microsoft.com/en-us/cpp/build/reference/arch-x64?view=msvc-170).

## Mandat proposé — préparation et un build CPU

1. Dans `C:/wt/distcpu-l2-reprise`, relever branche, diff, ressources actives et espace libre. Préserver tous les changements préexistants, les modèles, preuves, caches et DLL historiques. Établir la disponibilité hors ligne des sources NeMo `6a3ca369370782acee0dd155e34394ba60b920c4`, llama `bd4f514db14d87fded667787a7a963bfbaa98e89`, vcpkg `9e593bb18ea69cc5095e012465dcd675a822ed0d`, patches et outils épinglés. Si l’un manque, arrêter et présenter le besoin ; aucun téléchargement n’est inclus.
2. Préparer dans `native/build-config.json`, `ci/build-native.ps1` et, si nécessaire, `ci/guard-native.ps1` et leurs tests directement concernés, un profil CPU portable explicite, distinct du profil historique. Valider effectivement toutes les options ISA et refuser les flags contradictoires, notamment `/arch:AVX*` et `-march=native`. Les changements de dépendances, manifestes Cargo et de sources tierces exigent un mandat distinct.
3. Adapter dans la garde native, avant lancement et sous revue, le contrôle WHEA déjà utilisé par `ci/qualify-native.ps1` : relever la référence du journal System et le dernier numéro d’événement du fournisseur WHEA-Logger, puis vérifier au plus toutes les cinq secondes les nouveaux événements pendant la famille de processus du build. Conserver la référence et les événements détectés dans la racine du lot. Couvrir en auto-tests les cas absence, nouvel événement et erreur de lecture. Faire relire indépendamment le diff, les auto-tests positifs et négatifs, la conservation du profil historique, la garde et la gestion d’arrêt. Corriger les constats dans la limite de deux cycles. Les sorties attendues sont sous `C:/wt/distcpu-l2-reprise/target/native-build/cpu/parakeet-portable-cpu1/` et l’espace de build sous `C:/wb/native/cpu` selon `ci/native-workspace.ps1`. Si ces chemins sont occupés ou les caches indisponibles, arrêter sans effacer ni remplacer.
6. Après succès, contrôler les options CMake effectives, flags et définitions de tous les objets et bibliothèques liés, les cinq DLL, PE, exports, dépendances, empreintes et désassemblage de l’initialisation. Rechercher les instructions avancées dans le code produit, y compris intrinsèques et dépendances vcpkg ; documenter les limites de couverture de l’analyse. Un cache CMake seul ne vaut pas preuve de portabilité. Conserver les logs et les résultats de contrôle sous la racine du lot.
