La cible CPU et la matrice Windows sont distinctes. x86-64-v2 décrit un niveau de capacités processeur, tandis que Microsoft documente Windows 11 par exigences système et listes de modèles de processeurs pris en charge. À la date de ce cadrage, la page Microsoft indique que le support Home/Pro de 24H2 a pris fin le 10 novembre 2026, alors que 25H2 et 26H2 sont encore listées comme versions supportées. Cela rend 24H2 impropre comme recommandation générique grand public sans vérifier l’édition ; c’est une recommandation à confirmer, pas une décision utilisateur. ### Parcours et états visibles

- **UC-01 — Installer et démarrer.** L’installeur présente ses prérequis, examine le CPU, puis refuse avec une cause compréhensible ou autorise la progression. Après installation, le premier lancement résout les ressources prévues ou indique laquelle manque. L’état `installé` ne signifie pas encore que le premier lancement a réussi.
- **UC-02 — Sélectionner le chemin CPU.** Au lancement, les capacités sont lues dans le contexte pertinent. Le chemin de base est utilisé lorsque v2 est admissible. Toute variante facultative est évaluée avant le démarrage du worker qui l’exécute. Une incapacité de lecture ne rend pas une variante optimisée admissible.
- **UC-03 — Refuser un CPU sous v2.** L’installeur affiche l’exigence minimale et les capacités manquantes, puis se termine sans créer ou remplacer fichiers, réglages, raccourcis ou enregistrement de l’installation. Le point d’entrée de l’installeur doit lui-même s’exécuter sur le témoin qui sera refusé.
- **UC-04 — Installer depuis un environnement propre.** L’utilisateur suit les instructions sur un poste qui ne contient ni dépôt, ni outils de build, ni caches de développement. Les modèles, runtimes et redistribuables requis sont soit dans l’édition, soit obtenus par la procédure exacte annoncée.
- **UC-05 — Importer et enregistrer le micro.** Le mode CPU importe WAV/MP3 et transcrit le micro selon les sorties existantes. Le texte micro confirmé reste visible par blocs ; arrêt normal ou fermeture produit les TXT/SRT/WAV attendus. Les limites existantes de qualité, vitesse, capture et fermeture restent les références, sans seuil CPU supplémentaire.
- **UC-06 — Exercer le même paquet en CI.** La CI rattache chaque résultat au même candidat x64. Une exécution est positive uniquement si l’installation, le lancement et une courte inférence sont observés ; un build vert ou un détecteur simulé seul ne suffit pas.
- **UC-07 — Préserver GPU NVIDIA/Auto.** Si ces chemins sont inclus dans l’édition ou touchés par des composants partagés, les sélections CPU/GPU manuelles et la politique Auto restent celles déjà acceptées. GPU manuel ne bascule pas automatiquement ; Auto garde son unique tentative CPU avant traitement après échec GPU d’initialisation.

## 5. Architecture et décisions techniques

Le cœur définit le prédicat d’admissibilité et les transitions métier. L’adaptateur CPU lit CPUID avec une API sûre et bornée, puis reporte les capacités observées. L’application choisit le chemin CPU admissible avant d’initialiser le worker. Desktop présente les causes. La racine `whisper-desktop` compose le profil de distribution. La couche de build ferme les flags et ressources du desktop et du worker. L’installeur effectue son préflight avant l’engagement. CI exécute le candidat et conserve l’identité de l’artefact et des environnements.

Le prédicat v2 utilise une lecture CPUID explicite dans le processus concerné, via l’API sûre `std::arch::x86_64::__cpuid` de la toolchain épinglée Rust 1.98.1 ; aucune dépendance ou FFI n’est nécessaire. Lire les feuilles maximales 0 et `0x80000000`, puis exiger la disponibilité des feuilles 1 et `0x80000001`. Le plancher requiert `CPUID.1:ECX` bits 0 (SSE3), 9 (SSSE3), 13 (CMPXCHG16B/CX16), 19 (SSE4.1), 20 (SSE4.2), 23 (POPCNT) et `CPUID.80000001:ECX` bit 0 (LAHF/SAHF). Une feuille indisponible ou lecture incomplète produit `indéterminé`, jamais une admission. La macro `is_x86_feature_detected!` ne donne pas à elle seule une preuve complète car elle n’expose pas LAHF/SAHF. Vérifier cette API dans la source Rust épinglée : [stdarch x86 CPUID](https://github.com/rust-lang/rust/blob/1.98.1/library/stdarch/crates/core_arch/src/x86/cpuid.rs#L25-L115). Les critères d’instructions au-dessus de v2 couvrent notamment AVX, AVX2, FMA, F16C, BMI1/2 et toute extension livrée ; toute variante AVX doit aussi contrôler l’état OS requis. La classification de niveaux suit la [spécification x86-64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/low-level-sys-info.tex). Aucune `unsafe` n’est justifiée par ce design.

Pour la première édition, la recommandation technique est un chemin Turbo CPU portable et sans variante AVX2 distincte. Si le périmètre produit le permet, différer les variantes optimisées évite d’ajouter une seconde frontière d’exécutable et de dépendances. Si une variante accélérée est retenue, l’option proposée est un second worker lancé après détection, au-dessus de l’IPC existant, jamais chargé dans la branche CPU de base. Cette décision ne remplace pas l’exigence d’examiner les options CMake natives et les instructions effectives de chaque build.

Le profil de build futur doit fixer explicitement l’ISA pour Rust **et** le C/C++ de `whisper-rs-sys`/GGML ; le `target-cpu` Rust seul ne gouverne pas les sources CMake. Il faut relever les valeurs CMake et lignes de compilation réelles et vérifier tous les EXE/DLL atteints lors d’une transcription. Une sortie `GGML_NATIVE=OFF` ou un build réussi ne suffit pas comme preuve.

L’installeur doit être compilé au socle x64 lui permettant d’afficher le refus sur le témoin sous v2, indépendant du worker et du modèle, puis sortir avant copie, réglage, raccourci ou inscription du produit. Si la matrice Windows choisie ne permet aucun environnement supporté qui exécute l’installeur sous v2, le critère de refus réel et la portée supportée devront être arbitrés avant le lot. L’utilisation de `whisper-bootstrap` est une option à valider ; le format du paquet et l’interface de l’installeur sont ouverts.

Chaque environnement doit être accessible et reproductible. Le masquage de capacités Prism est facultatif et n’est requis que pour une preuve distincte qui l’utilise. |

Le poste hôte CPU x64 et l’ARM64 sous Prism sont deux jobs indépendants. Microsoft documente Prism x64 sous Windows on Arm et la capacité de masquer certains nouveaux jeux d’instructions par exécutable dans l’interface de compatibilité ; aucune méthode automatisée CI pour cette option n’est établie ici. Le futur plan ne doit pas prétendre qu’un runner `windows-latest` est un témoin v2 sans avoir mesuré ses capacités. [Émulation x64 Prism](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation) · [Réglages d’émulation](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-program-compat-troubleshooter) · [Détection architecture WoW64](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-iswow64process2)

Un SPIKE de compatibilité Turbo est un prérequis proposé au plan, mais requiert un mandat d’exécution distinct avant toute compilation. Son périmètre : inspecter les flags de toutes les unités Rust/C/C++ du chemin Turbo épinglé, établir ou obtenir un témoin v2 complet sans AVX et sans extensions supérieures, puis tenter une inférence courte du candidat. Succès : même candidat démarre et infère, capacités observées dans chaque processus natif, aucun flag ou instruction obligatoire au-dessus de v2. Arrêt : après trois essais ou 30 minutes, si le témoin ou la méthode ne sont pas disponibles ; remettre hypothèses, preuves et coût suivant. Propriétaire à désigner au lancement du lot. Aucun code produit, activation de CI distante ni build de DLL natives dans ce SPIKE. Toute construction BUILD-NATIF reste suspendue et exige une décision précise distincte ainsi que sa voie gardée. Le cadrage n’a exécuté aucune compilation et ne ferme pas ce risque.

**Décisions et prérequis de planification :**

- **D-01 — Windows pris en charge, accepté par l’utilisateur.** Windows 11 Home/Pro dans les versions encore supportées à la date de publication. Enterprise/LTSC et Windows on Arm ne sont pas des cibles de support public par défaut ; le test ARM64 exigé reste une qualification CI du binaire x64 sous émulation. Le plancher v2 reste une dimension distincte.
- **D-02 — Édition publique, acceptée par l’utilisateur.** `large-v3-turbo` avec les parcours CPU, NVIDIA et Auto existants ; Parakeet est exclu de cette édition.
- **D-03 — Installation, acceptée par l’utilisateur.** Installation neuve. Mise à jour, désinstallation, migration et rollback sont hors de cette première livraison. Le format, les effets précis et l’interface sont à définir dans le plan sans supposer une technologie hors stack.
- **D-04 — Qualification CI, exigence acceptée.** Deux jobs indépendants exécutent le même paquet x64 : témoin v2 sans AVX, et Windows ARM64 sous émulation. Le plan doit commencer par vérifier l’accès aux bancs et leur reproductibilité ; le workflow existant n’est pas réintroduit implicitement.
- **D-05 — Compatibilité native Turbo, gate technique.** Le chemin exact n’a pas encore été qualifié au plancher. Le plan doit placer la preuve de flags et d’inférence avant la livraison du paquet. Les builds DLL BUILD-NATIF restent suspendus et exigent une décision précise distincte et la garde `ci/build-native.ps1`.

**Readiness au 15 novembre 2026 : cadrage toujours hors `DESIGN READY`.** L’hôte observé est Windows 11 Pro build 26200 et Intel Core i9-14900K. Le contrôle .NET `IsSupported` a retourné vrai pour SSE3, SSSE3, SSE4.1, SSE4.2, POPCNT ainsi que AVX, AVX2, FMA, BMI1 et BMI2 ; cela confirme que ce poste dépasse le plancher, mais ce n’est pas une lecture CPUID complète ni un témoin v2 sans AVX. Deux PE historiques Whisper sont présents et passent le contrôle statique d’imports (desktop SHA-256 `c3da165351d27f76ba0bd898dc1b090c4a31cc24caeae44e9dc43ddece464d8a`, worker CPU SHA-256 `eb33d96b57ee47e5dcbe3238467df4f5656d055757374dbff5d58a5f751bbfef`) sans import CUDA ; ils ne sont pas le candidat portable et leur lancement/inférence n’a pas été essayé.
