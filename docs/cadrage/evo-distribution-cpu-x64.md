## 5. Architecture et décisions techniques

Le cœur définit le prédicat d’admissibilité et les transitions métier. L’adaptateur lit CPUID dans le desktop/bootstrap ; `whisper-worker-common`, déjà dépendance des workers CPU et GPU, fournit la lecture dans chaque processus worker. Les capacités brutes et la décision restent définies par le cœur. Chaque processus émet au démarrage un enregistrement local, versionné et borné, uniquement vers des handles redirigés par la qualification. Pour tout worker, stdout reste exclusivement le flux IPC typé ; la ligne de capacités est écrite uniquement sur stderr. L’adaptateur conserve la ligne allowlistée attribuée au PID/PE enfant tout en continuant de drainer stderr. Aucun réseau, identifiant persistant ou nouvelle donnée utilisateur. La collecte est best effort et ne retarde ni admission ni `Ready`. L’application choisit le chemin CPU admissible avant d’initialiser le worker. Le pilote externe T02 observe le GUI du candidat et capture ces lignes attribuées au PID/PE exact ; méthode UIA/runner non reproductible = `NOT RUN`. Le format du paquet et l’installeur restent les tâches T24/T31.

Le prédicat v2 lit CPUID dans chaque processus qui doit l’appliquer, via l’API sûre `std::arch::x86_64::__cpuid` de la toolchain épinglée Rust 1.98.1 ; aucune dépendance ou FFI n’est nécessaire. Le niveau v2 exige `CPUID.1:ECX` bits 0 (SSE3), 9 (SSSE3), 13 (CMPXCHG16B/CX16), 19 (SSE4.1), 20 (SSE4.2), 23 (POPCNT), et `CPUID.80000001:ECX` bit 0 (LAHF/SAHF), en plus du socle x86-64 v1. Feuilles absentes ou lecture incomplète donnent `indéterminé`. Le témoin du plancher doit avoir toutes les capacités v2 et aucune capacité v3 ou v4 selon la [spécification x86-64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/low-level-sys-info.tex) ; les extensions hors profils normalisés sont couvertes par l’inspection des commandes et instructions des images effectivement chargées. L’état OS requis pour AVX est distinct des bits CPUID bruts et doit être vérifié pour toute variante AVX. La source Rust épinglée décrit l’API sûre [stdarch x86 CPUID](https://github.com/rust-lang/rust/blob/1.98.1/library/stdarch/crates/core_arch/src/x86/cpuid.rs#L25-L115). Aucune `unsafe` n’est justifiée par ce design.

Pour la première édition, la recommandation technique est un chemin Turbo CPU portable et sans variante AVX2 distincte. Si le périmètre produit le permet, différer les variantes optimisées évite d’ajouter une seconde frontière d’exécutable et de dépendances. Si une variante accélérée est retenue, l’option proposée est un second worker lancé après détection, au-dessus de l’IPC existant, jamais chargé dans la branche CPU de base. Cette décision ne remplace pas l’exigence d’examiner les options CMake natives et les instructions effectives de chaque build.

Le profil de build futur doit fixer explicitement l’ISA pour Rust **et** le C/C++ de `whisper-rs-sys`/GGML ; le `target-cpu` Rust seul ne gouverne pas les sources CMake. Il faut relever les valeurs CMake et lignes de compilation réelles et vérifier tous les EXE/DLL atteints lors d’une transcription. Une sortie `GGML_NATIVE=OFF` ou un build réussi ne suffit pas comme preuve.

L’installeur doit être compilé au socle x86-64 v1 afin de s’exécuter sur un environnement x64 sous le plancher v2 et d’afficher le refus, indépendant du worker et du modèle, puis sortir avant copie, réglage, raccourci ou inscription du produit. Si, une fois les machines accessibles, aucun environnement de la matrice Windows retenue ne permet de démontrer ce refus réel, arbitrer la portée avant qualification publique ; le refus réel demeure un gate de distribution. L’utilisation de `whisper-bootstrap` est une option à valider ; le format du paquet et l’interface de l’installeur sont ouverts.

Pour l’émulation ARM64, prouver l’architecture via l’OS et le PE x64 pur ; une valeur `IsWow64Process2` ambiguë ne suffit pas. Références : [émulation x64 Prism](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation), [réglages d’émulation](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-program-compat-troubleshooter), [`IsWow64Process2`](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-iswow64process2), [ProcessMachineTypeInfo](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_machine_information). Le protocole desktop est préparé en T02 ; runner/UIA indisponible ou non reproductible signifie `NOT RUN`, sans substitut par un worker seul.

Les essais x86-64-v2 et Windows on Arm sont différés à la qualification du candidat : les builds et contrôles de codegen pourront être faits dans L1–L3 sur les moyens disponibles, mais l’inférence au plancher et les deux jobs CI attendent l’accès aux plateformes. **Décisions et prérequis de planification :**

- **D-01 — Windows pris en charge, accepté par l’utilisateur.** Windows 11 Home/Pro dans les versions encore supportées à la date de publication. Enterprise/LTSC et Windows on Arm ne sont pas des cibles de support public par défaut ; le test ARM64 exigé reste une qualification CI du binaire x64 sous émulation. - **D-02 — Édition publique, acceptée par l’utilisateur.** `large-v3-turbo` avec les parcours CPU, NVIDIA et Auto existants ; Parakeet est exclu de cette édition.

Toute création/activation de workflow reste soumise à un mandat précis.
