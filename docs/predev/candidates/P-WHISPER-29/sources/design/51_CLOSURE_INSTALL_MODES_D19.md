## INSTALL — exécution locale sans capacité réseau

`e1_offline.py` a recopié dans le dossier privé d’un AppContainer Windows les deux EXE, trois DLL CUDA privées et le modèle de `e1-install/primary` ; les six paires ont des SHA256 identiques et les tailles sont consignées dans `e1-offline-report.json`. Les sources `appcontainer-launch.cpp` et `network-probe.cpp`, le script de build et les quatre logs d’exécution sont manifestés dans `evidence/d19/`. L’AppContainer `WhisperDesignD19Offline` a zéro capacité réseau ; le launcher vérifie `TokenIsAppContainer=1` pour chaque enfant. Selon la [documentation Microsoft AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), sans capacité réseau le processus ne peut pas accéder au réseau. Un témoin TCP vers `127.0.0.1:8765` se connecte hors conteneur puis échoue (`WSA 10060`) dans ce même conteneur. Les workers CPU et GPU y chargent le modèle local exact, transcrivent le même WAV, terminent avec code 0 et rapportent leur backend respectif. Le modèle et les exécutables hashés correspondent au payload retenu, sans transfert réseau par ces processus. Les logs montrent les paramètres et l’identité du jeton. Le profil Windows est un banc d’isolation, non le packaging produit prévu.

Ce résultat ferme la lacune de preuve offline de D18 dans ce banc. Il n’éprouve ni PC propre, ni runtime absent, ni installateur final, ni acquisition HTTPS/redirections externe ; ces éléments restent préflight/qualification ultérieurs. Le modèle n’est pas fourni dans le corpus documentaire en raison de sa taille : hash/taille et Ready original sont manifestés en D18, et la copie exacte est contrôlée dans le rapport D19.

## MODES — erreur worker et validation commune

Le nouveau worker `engine_attested.rs` installe un callback natif versionné, crée contexte puis state, et contrôle les logs `CUDA0`/CPU **avant** `state.full`. Une demande GPU qui n’atteste pas CUDA0 échoue sans lancer `state.full` ; le log `engine-attested-gpu-absent` le démontre avec `CUDA_VISIBLE_DEVICES=-1`. CPU et GPU réussis émettent `backend_attested=... before_full=true`. Le même worker accepte une injection `fail-after-inference` qui quitte réellement avec code 73 après un calcul GPU attesté.

Le contrôleur `e2_state.rs` reçoit les événements processus dans une méthode commune `Controller.accept`. En strict, code 73 donne `Stopped`, sans lancement CPU ni insertion dans `committed`. En Auto, le même code 73 invalide génération 1 et choisit CPU. Un résultat GPU génération 1 réellement calculé est ensuite livré au même validateur : il est rejeté avant le chemin `committed.push`. La fenêtre 2 est rejouée sur l’EXE CPU à 15960–22500 ms ; les trois fenêtres publiées portent 0–14460, 15960–22500, 24000–30000 ms sans chevauchement et les générations 1/2 attendues. `e2-state-report.json` lie SHA des sources, locks, deux EXE et logs ; le run se termine 0. L’injection 73 n’est pas une panne physique de pilote, le commit du banc est en mémoire, et le produit final n’existe pas.
