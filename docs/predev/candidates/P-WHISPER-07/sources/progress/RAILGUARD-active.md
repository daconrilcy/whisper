# Railguard actif — Whisper Windows V1

**Portée active :** tout code Rust, build, installateur et données de migration du produit Whisper Windows V1. Activé par HUMAN-USER, autorité de gouvernance compétente, dans `RAILGUARD.md` à la racine du dépôt le 2026-10-05. Source revue : D-WHISPER-19, hash consigné dans `docs/predev/railguard-activation-L00.md`. Le texte actif conserve à effet normatif identique les règles RG-01 à RG-10 et les contrôles de préflight.

| ID | Règle et propriétaire | Contrôle requis / exception |
|---|---|---|
| RG-01 | `domain` pur, `application` dépend du domaine et de traits de ports ; `adapters` implémente les ports ; `ui` appelle l'application ; composition root assemble. Owner : architecte Rust. | Matrice `08`, revue imports/features et test de compilation de l'application sans adaptateurs natifs ; tout changement de frontière via CHANGE revu. Pas d'exception tacite. |
| RG-02 | Une seule capture live ; import actif mutuellement exclu ; file FIFO durable séparée de l'historique ; aucune exécution restaurée sans choix. Owner : domaine/application. | Tests de transitions `UC-01/03/04/12` incluant crash et répétition de commandes. Changement produit : réponse utilisateur et nouvelle revue. |
| RG-03 | Aucun accusé de fragment/file sans confirmation durable ; aucune perte audio silencieuse ; dernière plage non confirmée mesurée et annoncée. Owner : stockage/capture. | Injection de coupure/saturation `SPIKE-02`, tests de contrat `AC-12/13`, journal de pertes ; fréquence/borne documentées. Une dérogation à la garantie exige changement de périmètre autorisé. |
| RG-04 | Source importée immuable ; retrait de file/annulation ne la suppriment jamais ; suppression d'archives uniquement après confirmation explicite et inventaire exact. Owner : stockage/application. | Tests `AC-03/10/12/18` et chemin source hashé avant/après. Aucune suppression élargie par convenance. |
| RG-05 | Les artefacts requis par **type de job** ne sont Complete qu'avec preuve de cohérence : live un MP3 par passage plus TXT/SRT cumulés dans un dossier de transcription ; import TXT/SRT et référence à la source intacte, sans copie audio par défaut. | RG-06 | GPU actif affiché seulement si backend effectif prouvé ; Auto signale CPU et déduplique ; GPU forcé ne replie qu'après choix. Owner : moteur/application. | Essais natifs et logs de backend `SPIKE-01`, tests `AC-07`; CPU/GPU Python n'est pas une preuve. |
| RG-07 | Worker et IO bloquants hors UI ; canaux bornés ; shutdown versionné et résultats périmés rejetés ; unsafe limité à l'adaptateur natif avec commentaire d'invariant et test. Owner : architecte Rust. | Revue des canaux, métriques de saturation, tests d'arrêt et inspection de chaque `unsafe`. Exception uniquement via ADR/CHANGE et preuve de sûreté. |
| RG-08 | Aucun audio/texte envoyé au réseau ; réseau admis pour téléchargement du modèle pendant installation seulement, avec hash/licence/source figés. Logs locaux suivant Q-09. Toute télémétrie future exige décision produit. |
| RG-09 | Versions de crates, toolchain, modèle, backend natif et DLL figées avec hashes/lockfile ; build CPU et GPU, package installable et migration de paramètres vérifiés. Owner : build/release. | `cargo fmt --check`, tests verrouillés, Clippy strict pertinent, builds CPU/GPU, inspection de package et smoke natif cible ; versions exactes définies par `SPIKE-01`. Pas de release si une variante promise échoue. |
| RG-10 | Chaque changement structurel conserve source, raison, IDs impactés, migration/compatibilité, nouvelle identité manifestée et revue ; lot ne démarre qu'après preflight et autorisation de coder distincte. Owner : coordinateur/architecte. | Ledger CHANGE, contrôle manifeste et gate selon `handoff-contract.md`; aucun CLEAN réutilisé après changement d'octets. |

## Préflight de chaque lot futur

Vérifier source et autorité du design READY, exactitude manifest/digest/revue CLEAN, décisions Q nécessaires, preuve des SPIKE applicables, état de l'activation du railguard et SHA actif, branche/checkout, dépendances et migration. Un lot dépendant d'un détail Q encore ouvert attend ce détail ; les autres peuvent être planifiés après gate DESIGN. Une divergence du code source initial ou des preuves d'exécution suspend seulement les lots touchés jusqu'à analyse CHANGE.

## État

Actif par l'acte de gouvernance HUMAN-USER du 2026-10-05. La portée et les règles restent celles de la proposition D19 revue.

## Deltas techniques proposés ARCH-D18

RG-01 : matrice core/application/adapters/worker/desktop et builds CPU/GPU séparés contrôlés par imports. RG-03 : ACK après sync audio+texte, acquisition/confirmation/perte séparées et capacités par étage. RG-05 : pending avant capture, générations immuables, manifeste/hashes/pointeur dernier, récupération idempotente. RG-06 : deux workers, attestation backend versionnée, strict sans CPU automatique, Auto génération suivante. RG-07 : enfant isolé et contrôle UI hors canal data, Quitter maintenu ouvert sans choix. RG-08 : réseau seulement installateur/ModelStore et modèle pin/hash. RG-09 : VC Redist/driver, notices, imports/versions/signatures vérifiés. Ces deltas sont actifs dans le présent railguard ; leur preuve de placement avant code demeure requise selon le contrat de predev.
